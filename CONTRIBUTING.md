## Как внести вклад

### Идеи и ошибки

Начните с [Issues](https://github.com/pipedude/yahont-ce/issues). Опишите
проблему или идею: что вы хотите сделать и зачем. Для ошибки добавьте версию
(тег выпуска `vX.Y.Z` или хэш коммита), шаги воспроизведения и логи.

Если вы нашли уязвимость, **не создавайте Issue**. Напишите на
support@yahont.ai, как описано в [SECURITY.md](SECURITY.md).

### Pull request

1. Для большого изменения сначала создайте Issue и обсудите его. Не все
   предложения мы принимаем: нужно сохранить баланс между возможностями и
   сложностью продукта.
2. Сделайте fork репозитория и ветку от `main`.
3. Внесите изменение. Держите pull request небольшим: не больше 500 строк
   реальных изменений.
4. Добавьте тесты и пройдите [проверки](#проверки-перед-pull-request).
5. Откройте pull request и опишите, что и зачем вы изменили.

**Как мы принимаем изменения.** Разработка Yahont ведётся в закрытом
репозитории. В `yahont-ce` публикуются снимки этого репозитория, и мы не вносим
в него коммиты напрямую. Поэтому мы не вливаем pull request кнопкой «Merge».
Принятое изменение мы переносим в основную ветку разработки вручную. Оно
попадает в `yahont-ce` со следующим выпуском. Мы укажем вас автором в сообщении
коммита и закроем pull request со ссылкой на выпуск.

**Лицензия вклада.** Код вне папок `ee` распространяется по лицензии MIT.
Отправляя pull request, вы соглашаетесь, что ваш вклад распространяется на тех
же условиях.

**Не меняйте папки `ee`.** Мы заменяем их копией из Onyx при каждой публикации
(см. [Папки ee](#папки-ee)).

## Подготовка окружения

Yahont CE зависит от внешних сервисов: PostgreSQL (база данных), OpenSearch
(поиск и векторный индекс), Redis (кэш), хранилище файлов и Nginx. В
`deployment/docker_compose/docker-compose.yml` они уже описаны.

### Что нужно установить

- **Python 3.13.** Версия указана в `.python-version`. Другие версии могут
  потребовать правок кода и зависимостей. Python 3.14 пока не поддерживается:
  у части зависимостей нет сборок под него.
- **[uv](https://docs.astral.sh/uv/).** Менеджер Python-пакетов.
- **[Bun](https://bun.sh).** Менеджер JavaScript-пакетов. Установка:
  https://bun.sh/docs/installation.
- **Docker** и Docker Compose. Нужны для запуска приложения.

### Backend

Из корня репозитория:

```bash
uv sync
```

Команда создаст окружение `.venv` и установит зависимости из `uv.lock`.
Для коннектора «Веб-сайт» нужен браузер для Playwright:

```bash
uv run playwright install
```

### Frontend

```bash
cd web
bun install
```

## Проверки перед pull request

В Yahont CE нет настройки `pre-commit`. Запускайте проверки вручную.

### Backend

Из корня репозитория:

```bash
uv run ruff check backend
uv run ruff format --check backend
uv run ty check
```

`ruff` проверяет стиль и форматирование, `ty` — типы. Код Python аннотирован
полностью, пусть так и остаётся.

Unit-тесты не требуют запущенных сервисов. Запускайте их из папки `backend`:

```bash
cd backend
uv run pytest tests/unit
```

Тесты `external_dependency_unit` и `integration` требуют запущенных сервисов.
Описание типов тестов и общих фикстур — `backend/tests/README.md` и
`backend/AGENTS.md`.

### Frontend

Из папки `web`:

```bash
bun run format:check   # проверка форматирования (oxfmt); bun run format исправит
bun run lint           # проверка кода (oxlint); bun run lint:fix исправит часть замечаний
bun run types:check    # проверка типов
bun run test           # тесты Jest
```

`lint` не должен сообщать об ошибках. Предупреждения сейчас есть и не блокируют
pull request, но не добавляйте новые.

Правила для интерфейса (компоненты Opal, переводы, стили) — `web/AGENTS.md`.
Новый текст в интерфейсе добавляйте в каталог переводов
`web/src/i18n/messages` для всех локалей.

## Запуск приложения

### В Docker

Поддерживаемый способ запуска — Docker. Из папки `deployment/docker_compose`:

```bash
cp env.template .env
openssl rand -hex 32   # вставьте результат в USER_AUTH_SECRET в файле .env
docker compose up -d --build
```

Откройте http://localhost:3000. Без `USER_AUTH_SECRET` сервер не запускается.
Флаг `--build` обязателен: он собирает образы из вашего кода. Без него Docker
Compose попробует скачать готовые образы `yahontai/*` из Docker Hub, а не ваш код.
После любого изменения кода выполните команду заново. Подробности — в
[README.md](README.md).

### Из исходников

Запуск сервисов из исходников с отладчиком для Yahont CE пока не описан: в
репозиторий не входят `docker-compose.dev.yml` и настройки отладчика. Мы
добавим этот способ позже. Пока проверяйте изменения unit-тестами и запуском в
Docker.

## Особенности macOS

Установите [Homebrew](https://brew.sh/), затем Python 3.13:

```bash
brew install python@3.13
```

Добавьте Python 3.13 в `PATH`: строка в `~/.zshrc`, затем откройте новый
терминал.

```
export PATH="$(brew --prefix)/opt/python@3.13/libexec/bin:$PATH"
```

Для Docker установите [Docker Desktop](https://www.docker.com/products/docker-desktop/)
и запустите его до команд `docker`.

## Engineering Best Practices (инженерные практики)

Эти практики мы унаследовали от Onyx и следуем им в Yahont. Файлы `AGENTS.md`
в репозитории ссылаются на этот раздел.

### Принципы и работа в команде

- **Двери в одну и две стороны.** Если решение легко отменить (дверь в две
  стороны), двигайтесь быстро и итерируйте. Если трудно (в одну сторону),
  действуйте осмотрительнее.
- **Согласованность важнее «правильности».** Предпочитайте единые приёмы по всей
  кодовой базе. Если что-то действительно плохо, исправляйте это везде.
- **Исправляйте то, что трогаете (выборочно).**
  - Не обязательно исправлять каждое нарушение практик, которое вы заметили.
  - Не вносите новые плохие практики.
  - Если ваше изменение затрагивает код с нарушением, исправьте его в этом же
    изменении.
- **Не «приклеивайте» функции.** Добавляя возможность, перестройте код логично,
  чтобы не засорять интерфейсы и не копить технический долг.

### Стиль и сопровождаемость

#### Комментарии и читаемость

Комментарии и docstring пишите на английском, коротко: что делает код и почему.
Не ссылайтесь на внутренние задачи и документы. Добавляйте понятные комментарии:

- на логических границах (например, у интерфейсов), чтобы читателю не пришлось
  копать на десять уровней вглубь;
- там, где сделано допущение или что-то неочевидное и неожиданное;
- для сложных потоков и функций;
- везде, где это экономит время (например, нетривиальные регулярные выражения).

#### Ошибки и исключения

- **Падайте громко**, а не пропускайте работу молча. Пример: пробросьте
  исключение, а не молча отбрасывайте документ.
- **Не злоупотребляйте `try/except`.**
  - Ставьте `try/except` на правильном логическом уровне.
  - Не скрывайте исключения, если это явно не оправдано.

#### Типизация

- Всё должно быть **как можно строже типизировано**.
- Используйте `cast` для неудобных или слабо типизированных интерфейсов
  (например, результат `run_functions_tuples_in_parallel`).
  - Применяйте `cast` только когда проверка типов видит `Any` или типы слишком
    общие.
- Предпочитайте типы, которые легко читать.
  - Избегайте плотных типов вроде `dict[tuple[str, str], list[list[float]]]`.
  - Лучше доменные модели, например:
    - `EmbeddingModel(provider_name, model_name)` как модель Pydantic;
    - `dict[EmbeddingModel, list[EmbeddingVector]]`.

#### Состояние, объекты и границы

- Держите **чёткие логические границы** у контейнеров состояния и объектов.
- В объекте **конфигурации** не должно быть, например, `db_session`.
- Избегайте контейнеров состояния с глубокой вложенностью и огромных плоских
  (решайте по ситуации).
- Предпочитайте **композицию и функциональный стиль** наследованию и ООП.
- Предпочитайте **отсутствие мутаций**, если нет веской причины.
- Объекты состояния должны быть **осознанными и явными**, лучше немутируемыми.
- Используйте интерфейсы и объекты, чтобы чётко разделять ответственность.
- Выбирайте простоту, если нет явной выгоды от сложности.
  - Избегайте переусложнённых механизмов вроде семафоров.
  - Предпочитайте **хэш-таблицы (словари)** деревьям, если нет веской причины.

#### Именование

- Называйте переменные внимательно и осмысленно.
- Если сомневаетесь, выбирайте длинные явные имена.
- Не используйте однобуквенные переменные, кроме небольших самодостаточных
  утилит (а лучше вообще не используйте).
- Сохраняйте одно имя для одного объекта по стеку вызовов и внутри функций,
  когда это разумно.
  - Хорошо: `for token in tokens:`
  - Плохо: `for msg in tokens:` (если перебираются токены)
- Имена функций делайте **длинными и описательными**, чтобы их легко искать по
  коду.
  - IntelliSense может пропустить места вызова, а поиск лучше всего находит
    уникальные имена.

#### Корректность по построению

- Предпочитайте самодостаточную корректность: не полагайтесь, что вызывающий
  «использует правильно», если можно затруднить неправильное использование.
- Избегайте избыточности: если функция принимает аргумент, она не должна
  принимать ещё и объект состояния, который содержит этот же аргумент.
- Никакого мёртвого кода (если нет очень веской причины).
- Никакого закомментированного кода в `main` и в ветках с функциями (если нет
  очень веской причины).
- Никакой дублирующей логики:
  - не копируйте код по веткам, если общую логику можно вынести выше условия;
  - если вы боитесь трогать оригинал, вы понимаете его недостаточно хорошо;
  - LLM часто создают неочевидные дубликаты логики: проверяйте внимательно и
    убирайте их;
  - избегайте «почти одинаковых» объектов, из-за которых непонятно, какой
    использовать.
- Избегайте очень длинных функций с цепочками логики:
  - выделяйте шаги во вспомогательные функции для читаемости, даже если они не
    переиспользуются;
  - «питоничные» многошаговые выражения допустимы в меру; не жертвуйте
    ясностью ради хитрости.

### Производительность и корректность

- Не удерживайте ресурсы надолго (сессии БД, блокировки, семафоры).
- Проверяйте объекты при создании и непосредственно перед использованием.
- Код коннекторов (данные → документы):
  - любую структуру в памяти, которая может расти без ограничения в зависимости
    от входных данных, нужно периодически проверять по размеру;
  - если коннектор падает по памяти (часто выглядит как «пропавшие задачи
    Celery»), проверьте это в первую очередь.
- Async и циклы событий:
  - не добавляйте новый async-код Python или код с циклами событий; по
    возможности делайте существующий async-код синхронным, если это разумно;
  - async-код без полного понимания и без конкретной причины скорее добавит
    ошибок, чем даст заметный выигрыш в скорости.

### Соглашения репозитория

#### Где лежит код

- Pydantic и модели данных: файлы `models.py`.
- Функции доступа к БД (кроме ленивой загрузки): папка `db/`.
- Промпты LLM: папка `prompts/`, структура примерно повторяет код, который их
  использует.
- Маршруты API: папка `server/`.

#### Pydantic и моделирование

- Предпочитайте **Pydantic** датаклассам.
- Если это действительно необходимо, используйте `allow_arbitrary_types`.

#### Соглашения о данных

- Предпочитайте явный `None` пустым строкам-заглушкам (обычно, зависит от
  замысла).
- Предпочитайте явные идентификаторы: строковые перечисления вместо числовых
  кодов.
- Избегайте «магических чисел» (при необходимости размещайте их рядом с кодом).
  **«Магических строк» избегайте всегда.**

#### Логирование

- Логируйте сообщение там, где оно создаётся.
- Не передавайте сообщения по цепочке только ради того, чтобы залогировать их в
  другом месте.

#### Инкапсуляция

- Не используйте приватные атрибуты, методы и свойства других классов и
  модулей.
- «Приватное» остаётся приватным: уважайте эту границу.

#### SQLAlchemy

- Ленивая загрузка часто вредит на больших объёмах, особенно для нескольких
  списковых связей.
- Будьте осторожны с доступом к атрибутам объектов SQLAlchemy:
  - он помогает избежать лишних запросов к БД,
  - но может упасть вне активной сессии,
  - а ленивая загрузка добавляет скрытые зависимости от БД в «простые»
    функции.
- Справка: https://www.reddit.com/r/SQLAlchemy/comments/138f248/joinedload_vs_selectinload/

#### Разработка от основной ветки и флаги функций

- **В pull request должно быть не больше 500 строк реальных изменений.**
- **Вливайте в основную ветку часто.** Избегайте долгоживущих веток с
  функциями: они создают конфликты слияния и трудности интеграции.
- **Используйте флаги функций для постепенного включения.**
  - Большие функции вливайте небольшими готовыми к выпуску частями за флагом.
  - Так интеграция идёт непрерывно, а незавершённая функциональность не видна
    пользователям.
- **Держите флаги недолго.** Когда функция полностью включена, быстро удаляйте
  флаг и мёртвые ветки кода.
- **Ставьте флаг на правильном уровне.** Лучше флаг на входе в API или
  интерфейс, чем глубоко в бизнес-логике.
- **Тестируйте оба состояния флага.** Код должен корректно работать и с
  включённым, и с выключенным флагом.

#### Прочее

- Каждый `TODO` в коде должен содержать имя или логин ответственного либо номер
  Issue, которое описывает эту работу.
- Избегайте логики уровня модуля, которая выполняется при импорте (побочные
  эффекты при импорте). Любая значимая логика должна быть внутри функции,
  которую вызывают явно. Допустимые исключения: чтение переменных окружения и
  настройка логгеров.
  - Если вам нужно что-то подобное, вынесите логику в отдельный файл для
    ручного запуска (с `if __name__ == "__main__":`), который ничто не
    импортирует.
- Не смешивайте скрипты Python для запуска из командной строки (с
  `if __name__ == "__main__":`) и модули для импорта. Если по неочевидной
  причине это один файл, всю логику запуска (включая импорты) держите внутри
  блока `if __name__ == "__main__":`.
  - Как правило, исполняемые файлы лежат в `backend/scripts/`.

локально командой `docker compose up -d --build`.

## Папки ee

Yahont CE не содержит серверной части Enterprise Edition (`backend/ee`).
Папки `web/src/ee` и `web/src/app/ee` — копии из Onyx без изменений, под
лицензией Onyx Enterprise License (файл `LICENSE` в каждой папке). Мы не
принимаем изменения в эти папки: при каждой публикации они заменяются версией
из Onyx.
